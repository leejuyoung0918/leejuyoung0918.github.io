SBOM Vulnerability Analysis

Which assets should you check when a vulnerability is disclosed?
I built a tool that takes a vulnerability ID, finds the assets containing the affected component and shows the scan evidence behind each match.

Period
September 2026 – present
My role
Built the scan pipeline, API and search interface
Tools & methods
Python, FastAPI, NetworkX, Cytoscape.js

Connecting two scanners’ findings

Syft generates a software bill of materials (SBOM), and Trivy identifies known vulnerabilities. The two scanners can use different names for the same package or scan an asset at different times. I converted both outputs to a common format and created a snapshot for each asset scan, linking it to the components and vulnerabilities observed at that point.

Tracing a result to its source

From a vulnerability, users can trace each match to an asset, a specific package version and the underlying scan. I labeled unscanned assets as undetermined and kept missing scores distinct from measured scores of zero. I shared the query logic across the command line, API and web interface so all three search and sort results consistently.

Testing with a patched control

I tested the tool against Log4Shell (CVE-2021-44228) using two assets containing Log4j 2.14.1 and a third patched to 2.17.1. In a local graph with 15,086 nodes and 16,508 edges, the query returned only the two assets with the vulnerable version. The test verified whether each asset contained the vulnerable component at scan time.
